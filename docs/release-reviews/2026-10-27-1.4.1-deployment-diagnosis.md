# 1.4.1 部署诊断记录（2026-10-27）

> 背景：用户长期反馈「一键切换不可用，每次都落入设置页保底流程」。本记录归档当日的根因诊断、实机验证与部署动作，供换机 / 重装系统后排查参考。

## 根因

**托盘常驻进程为 1.3.2 旧版**（`dist\BrowserSwitcher-1.3.2-win-x64\`），早于直切功能（1.4.0 引入、1.4.1 修复 Hash 时序）。代码本身没有问题——问题在部署版本滞后，开机启动 Run 键也指向旧路径。

## 三层障碍排查（Windows 默认浏览器保护）

| 障碍 | 本机结果（Win10 19045，补丁至 2026-03） |
| --- | --- |
| UCPD 内核拦截（2024-03 补丁起） | **不生效**：`UCPD.sys` 文件存在但服务未注册（`sc query UCPD` 报 1060） |
| http/https `UserChoice` 键 ACL | **开放**：owner 为当前用户，admin FullControl |
| .htm/.html `FileExts\UserChoice` 键 ACL | **受限**：admin 有显式 `SetValue Deny`（微软标准保护；可经「删键重建」绕过，Deny 不含 DELETE。当前实现为尽力写入，失败不影响 http/https 判定） |

## 实机验证

`RUN_LIVE_SWITCH_TESTS=1 dotnet test --filter "FullyQualifiedName~LiveSwitch"`
（1.4.1 源码，含 f3542b4 时间戳修复）：

- Chrome ↔ Brave 往返 **7 次切换全部成功**（含 3 轮连续往返模拟多次托盘切换）
- 结束状态恢复为 BraveHTML，与测试前一致

## 部署动作

1. 结束 1.3.2 进程
2. HKCU Run 键 `BrowserSwitcher` 指向 `dist\BrowserSwitcher-1.4.1-win-x64\BrowserSwitcher.exe`
3. 启动 1.4.1；核对发布包 ProductVersion 为 `1.4.1+f3542b4`（确认含时间戳修复）

## 边界与后续

- 若重装系统或后续补丁启用 UCPD 服务，内置直写将被内核拦截（写入静默失败）。届时按应用内提示走 `Tools\SetUserFTA.exe`（2.1+）或「禁用 UCPD + 重启」。
- 同日清理：删除一次性工具 `tools/IcoTool`（tray.ico 已入库）与 `tools/SwitchProbe`（诊断能力由 LiveSwitch 测试覆盖）及对应审核记录，`tools/IcoTool/*` 的 .gitignore 规则一并移除。

## 附：`.htm/.html` 直写实验结论（2026-10-27 当日追加）

曾尝试把 `.htm/.html` 关联改为「删键重建」直写（Firefox 同源思路），实机三轮验证后**放弃并回滚**：

1. **动态 ACL 保护**：删除 `.htm/.html` 的 `UserChoice` 键后重建，新键会被系统**即时重新保护**（毫秒级竞争窗口，写入时好时坏）；失败时留下**无 ProgId 的空键**，比指向旧浏览器更糟（双击 .htm 弹「选择打开方式」）。
2. **系统自动跟随**：`http/https` 指向新浏览器且文件关联缺失时，系统会异步派生跟随的 `UserChoice`（含合法 Hash）——但延迟不可控（分钟级），不能作为产品逻辑依赖。
3. **http/https 删键同样有竞争**：删键后系统可能抢先重建受保护键，导致整体切换失败（实测 Live 第 2 段即栽于此）。

**结论**：保持 1.4.1 行为——`http/https` 就地写入（默认浏览器判定核心，7+ 次往返验证稳定），`.htm/.html` 尽力写入、失败保持旧值。此方向不再列为后续候选。
